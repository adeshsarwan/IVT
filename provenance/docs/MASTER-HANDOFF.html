Traffic Provenance Handoff

Checks whether an affiliate's visitors really came from the Google ads they claim to have bought. Written for a reviewer new to the code: what was already in the IVT before, what we added, how the pieces connect, how the data is stored, and what's left before going live.

In one minute

  • Problem: an affiliate can send bots, porn-site or junk traffic and call it "Google Ads". Google then penalises our ad account.
  • Check: every real Google ad click carries a unique gclid, and Google keeps a list of every gclid it billed. Each day we pull that list and match it against the gclids that reached our sites. We also compare counts: our visits vs Google's clicks.
  • Result per affiliate: OK WATCH THROTTLE BLOCK. A BLOCK is only a recommendation: a person reviews it and turns ads off for that affiliate by hand.
  • Manual for now: while we validate the results, nothing is blocked automatically. People review every BLOCK. Automatic blocking is one config switch for later (section 5).
  • Fit: a separate service. The existing code got one small change (Hook A, built, off by default). The kill switch it acts through (Hook B) already existed in Ad Pass.
  • Status: engine, ClickHouse storage, batch job, Hook A and tests are built and run locally against a fake Google API. Not deployed. No real Google token yet. Google only; Meta later.

3How it connects: an independent service, two hooks

Provenance is its own service. It is joined to the existing code at two points: Hook A brings data in, and Hook B acts on the result.

Why independent

  • Different rhythm: IVT answers in milliseconds; Provenance needs a day of Google data.
  • Different volume: hundreds of millions of rows. D1 can't hold that; ClickHouse can.
  • If Provenance or Google is down, ads and IVT keep working.
  • It can ship, be tuned and be rolled back without touching the live path.

Why the IVT data can't be reused as is

  • IVT stores only a hash of the gclid (click_id_hash), so it can't be matched against Google's raw list.
  • traffic_sessions has no affiliate column.
  • The SDK forwards only gclid / utm_* today, not the campaign, network and placement values Google's tracking template adds.

4How the gclid check works

Match every gclid

Each gclid that reached us is looked up in Google's list for that affiliate's account.

  • matched: real paid click
  • not found: invented by a bot
  • malformed: forged or a literal {gclid}
  • foreign: real, but from another affiliate's account (copied)

Compare counts

  • Our visits ÷ Google's clicks, per day. Well above 1 means traffic is being added that was never bought.
  • Google clicks that never reached us. Usually a few %. Near 0% means the report was built from our own data (tampering).

Other checks

  • Display / partner-network share and blocklisted placements (porn, junk apps)
  • The same gclid from many IPs (replay)
  • 24/7 flat traffic, device mismatch, impossible timing

Verdicts use 95% confidence ranges and minimum sample sizes, so a small or noisy day never blocks anyone. Full rules: provenance/README.md. Visual explainer: docs/06-traffic-provenance-simple.html.

5Manual for now, automated later

For now, Traffic Provenance is manual. The system recommends; a person decides. We want to see real results line up with what we know about each partner before any traffic is cut off automatically.

Now · validation

  1. The job finds BLOCK for an affiliate.
  2. It opens one review item in D1 (provenance_review) with the evidence: match rate, foreign and malformed gclids, visits per click, placements.
  3. A person checks it against the partner's own Google Ads UI.
  4. If it's confirmed, they set the kill switch by hand:
    npx wrangler kv key put --binding IVT_CONFIG "ads:aff:42" off --remote
  5. Unblocking is also manual.

Nothing is ever written to KV by the job. This is the code default: enforcement.autoBlock = false.

Later · automated

  • Once thresholds are tuned and no false BLOCKs appear on partners we trust, set enforcement.autoBlock = true.
  • The job then writes ads:aff:<id> = off itself, using the same evidence and circuit breaker (2 bad windows, or one very clear one).
  • Recommended: automate one tier at a time (e.g. only "foreign/forged gclids" first), keep the audit log, and alert on every automatic block.
  • No other code change is needed; the switch already exists and is tested.

6ClickHouse data structure

ClickHouse holds the large raw data, hundreds of millions of rows. D1 holds only the small state: verdicts, partners and the review queue. Every raw table deletes its rows automatically after a set time (TTL).

TableOne row perKey columnsEngine · sort key · kept
landingsvisit to our site (from Hook A2)id, ts, site, aff, route, url, ip_hash, ua_hash, ua_device, gclid (taken from url automatically on insert)ReplacingMergeTree · (aff, ts, id) · daily partitions · 90 days
google_clicksclick Google billed (from click_view)aff, customer_id, date, gclid, campaign_id, ad_group_id, device, click_type, ad_network_type, imported_atReplacingMergeTree(imported_at) · (aff, date, gclid) · monthly partitions · 90 days
google_dailyaccount × day × campaign × networkaff, customer_id, date, campaign_id, ad_network_type, clicks (Google's own total)ReplacingMergeTree · 400 days
google_syncaccount × day sync attemptstatus (ok / no_access / error), click_rows, daily_clicks, time_zone, auto_tagging, error, synced_atReplacingMergeTree(synced_at) · 400 days
  • No duplicates: the tables are Replacing: re-syncing a day replaces it, and the newest import wins.
  • Fast gclid lookups: both gclid columns have a bloom-filter index.
  • Safe queries: every value is sent as a bound parameter ({d:Date}), never pasted into SQL.
  • Size: about 5M landings + 5M Google clicks a day for 100 partners, roughly 300M rows a month and around 30–60 bytes per row compressed verify on real data.

The match, in SQL (simplified)

-- our gclids for the day vs Google's clicks; "owners" = which affiliates' accounts Google billed the gclid to
WITH L AS (SELECT aff, gclid FROM landings WHERE toDate(ts, {tz}) = {d}),
     G AS (SELECT gclid, groupUniqArray(aff) AS owners FROM google_clicks FINAL
           WHERE date BETWEEN {d} - 1 AND {d} + 1 GROUP BY gclid)
SELECT aff,
  count()                                                AS landings,
  countIf(gclid != '' AND NOT match(gclid, '^[A-Za-z0-9_-]{20,512}$')) AS malformed,
  countIf(has(owners, aff))                              AS matched,   -- real paid click
  countIf(notEmpty(owners) AND NOT has(owners, aff))     AS foreign    -- copied from another affiliate
FROM L LEFT JOIN G USING gclid GROUP BY aff;
-- plus: Google clicks with no landing (unlanded share), and landings ÷ google_daily.clicks

7Getting Google's data: the token

Recommended model: one set of Google credentials owned by us. Each partner gives that one Google login read-only access to their ad accounts. No per-partner tokens to collect, rotate or lose.

One-time setup on our side owner: us · about 1 hour + Google's review

  1. Create a dedicated Google account for data access, e.g. ads-data@yourcompany.com. Not a personal account; it should outlive any one employee. Turn on 2-step verification.
  2. Create a Google Ads manager account (MCC) while signed in as that account: ads.google.com/home/tools/manager-accounts. It's free. It's needed to apply for API access.
  3. Apply for a developer token: in the MCC, Admin → API Center. Describe the tool truthfully: "internal, read-only reporting and click validation for affiliate traffic we monetise". A new token starts with limited access; then apply for Basic access (thousands of requests/day, enough for 100+ partners). Google reviews it; allow days to a few weeks. verify current access levels
  4. Create a Google Cloud project (console.cloud.google.com) → enable Google Ads API → OAuth consent screen → create an OAuth client ID. If the company uses Google Workspace, mark the app Internal to skip Google's app verification. verify scope review rules
  5. Generate one refresh token for the data account with the scope https://www.googleapis.com/auth/adwords (Google's OAuth Playground with your own client ID, or Google's sample auth script). It lets the job get short-lived access tokens without anyone logging in.
  6. Store the five values as secrets, never in chat, email, tickets or the repo: 
    GADS_DEVELOPER_TOKEN     from API Center
GADS_CLIENT_ID           from the OAuth client
GADS_CLIENT_SECRET       from the OAuth client
GADS_MCC_REFRESH_TOKEN   from step 5
GADS_MCC_ID              the manager account id (digits)
    Locally: a git-ignored .dev.vars file. Production: npx wrangler secret put <NAME> on the Provenance Worker only.

Also required from every partner (put it in the partner terms):

  • Auto-tagging ON, so every click carries a gclid.
  • Tracking template at account level: {lpurl}?cid={campaignid}&ag={adgroupid}&net={network}&dev={device}&plc={placement}
  • Tell us every Google Ads account id (customer id) they send traffic from. Traffic claiming an account we can't read is treated as unverified.

First test with real data

  • The five secrets go in a git-ignored .dev.vars file, typed in by the account owner. Never paste them into chat, tickets or email.
  • One partner adds the data email as read-only.
  • With the owner's go-ahead, run a read-only dry run for that one account: pull one day of clicks into the local ClickHouse and show the match report. Nothing is written to KV or production.
  • Until then, every run uses the fake Google API. No real Google calls have been made.

8How it runs

StepWhat happensWhere
CollectHook A2 sends each landing to a queue; the Provenance Worker inserts them into ClickHouse landings in batches.Queue → ClickHouse
SyncEvery 6 h, one job per partner pulls every click of yesterday and the day before (Google adds late clicks), plus Google's own click totals. Re-running replaces the day, so there are no duplicates.Google Ads API → ClickHouse
MatchClickHouse joins our gclids to Google's clicks; the rules engine turns windows of 5,000 visits (or 24 h) into verdicts.ClickHouse + engine
DecideCircuit breaker: escalates fast, recovers slowly. BLOCK needs 2 bad windows or one very clear one.D1
ReviewA BLOCK opens a review item with the evidence. A person applies or dismisses it; unblocking is also manual (section 5).D1 → person → KV
  • Isolation: one partner failing (revoked access, outage) never stops the others; their last verdict holds.
  • Cost on Google's side: about 4 API requests per account per run, however many clicks.
  • Retention: raw rows deleted after 90 days; daily totals and verdicts kept.

10Still to build or decide before going live

To build

  • Queue provenance + binding PROVENANCE_Q on the IVT Worker (not added to wrangler.jsonc yet, on purpose)
  • Review page: list open items with evidence; Apply writes the KV key and an audit log entry; Dismiss with a reason
  • Alerts on new review items (Slack or email)
  • Partner registry: add a partner, their account ids, which access option, status (last sync, errors)
  • Monitoring: failed syncs, dead-letter queue, stale data
  • Encrypted storage for partner tokens if we use their own OAuth grants

To decide

  • ClickHouse Cloud (managed) or self-hosted; check pricing on real volume
  • Raw gclid or hashed gclid at rest (section 2)
  • THROTTLE: build the reduced-ads key in Ad Pass, or stay on/off only
  • Partner terms: auto-tagging, tracking template, read access, consequences of a BLOCK
  • Thresholds after shadow mode (defaults are in code)
  • Who reviews BLOCKs, and how fast

Known limits

  • iOS app-campaign clicks carry gbraid/wbraid instead of a gclid; they're checked by daily totals only
  • Google's click list is available for the last 90 days only verify
  • Visits without aff (house traffic) have no per-affiliate switch
  • Meta not covered yet; it only offers counts, no click ids
